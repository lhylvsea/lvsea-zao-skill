# 评测与治理

## 触发回归

触发集至少分成四类：

- `should_trigger`：明确要创建、迁移、优化、评估、封装、治理或发布可复用 Skill；
- `should_not_trigger`：一次性回答、解释、翻译、普通文档或不创建 Skill 的文案；
- `near_neighbor`：看起来相近但只要 checklist、Prompt 或 README，不要完整 Skill 包；
- `adversarial`：使用“自动化”“模板”“能力”等泛词，检验 description 不会被关键词诱导。

每个案例保留 family、预期结果、命中的概念和失败原因。通过率不能替代语义审查；边界失败要回到 description 和排除项修复。

## 输出契约

创建型请求至少要明确：主入口、面向人的 README、目标平台、验证命令、风险边界和交付状态。公开或 governed 包还要有：manifest、interface、IR、先例台账、创建交接、版本一致性和发布/安装证据。

## 门禁状态

- `pass`：证据存在且满足要求；
- `warn`：可以继续，但必须在报告中写明风险或 `missing evidence`；
- `block`：不能声称该包已达到对应发布或治理级别。

## 公开声明

只宣称已经由命名证据支持的事实：例如“触发案例全部通过”“包结构校验通过”“已完成隔离安装”。没有 provider 实跑、人工盲评、真实客户端遥测、用户满意度或业务结果时，不使用“效果更好”“生产级”“世界级”等超出证据的表述。

## 失败路径

- 触发漏掉：补充真实自然说法，重新跑正例和近邻负例；
- 误触发：收窄 description，加入排除项和对抗案例；
- 包过重：把长说明移到 references，删掉没有被流程引用的资源；
- 权限扩大：降低为只读、要求显式授权，或增加回滚和审计；
- 发布失败：保留当前工作树和报告，修复阻断 gate，不绕过门禁直推默认分支。
